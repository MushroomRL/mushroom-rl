For Mushroom 2.1:
    * Improve the HistoryManager:
        - support HasNextAction agents with history_length > 1: HasNextAction.draw_action returns the stored next
          action without calling the history manager, so the manager's buffer is not advanced on that step
        - subclass for complex per-stream specifications: the base handles only the `offset` option, delegate
          richer specs (strides, structured/general lookbacks) to a subclass
        - support a list agent backend: the vectorized online path and every offline parse_* path raise, only
          the single-env online path works. A list dataset handed to a numpy/torch agent is unaffected, since
          parse_* converts it before walking it
    * Register array backends from the class statement, as the dataset containers do, so adding a backend means
      editing both. fix the similar issue with the to_<backend> method if possible
    * Improve replay memory:
        - vectorize SequenceReplayMemory.get
        - remove host-device sync each iteration (int(c_anchor)/int(boundary[...])) in SequenceReplayMemory for the frame-stacking path
    * vectorization of the TD policies: `EpsGreedy` and `Boltzmann` draw a single action regardless of the
      batch size, so a TD algorithm cannot run on a vectorized environment
    * vectorization of the numpy policy gradient algorithms (REINFORCE, GPOMDP, eNAC):
        - the parametric numpy policies (e.g. the Gaussian ones) draw a single action regardless of the batch size
        - `PolicyGradient.fit` iterates the samples and splits episodes on the stored `last`, which on a flat
          multi-env block runs one env's open episode into the next env's rows; it should use the parsed `last`
    * handle ExtraInfo correctly in ReplayMemory
      - currently ignored in circular-buffer phase; info is never read back during sampling
    * vectorized env rendering
      - render a single window by default instead of one per active env; optionally a grid viewer compositing all envs
    * Implement diff properly for recurrent approximators
      - TorchApproximator.diff is written for the feedforward calling convention, so it fails on
        RecurrentTorchApproximator: `lengths` is padded to 2-D and breaks pack_padded_sequence, `lengths` is not
        defaulted to ones as predict does, and the observation gets only the batch pad instead of the batch and
        sequence pads applied by _pad_sequence
      - multi-output networks (e.g. RecurrentActorNetwork, returning action and next hidden state) are rejected by
        an assertion, since there is no single matrix packing gradients of outputs of different shapes
